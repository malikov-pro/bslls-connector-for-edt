# Потоки проверок в EDT и каналы BSL LS

Как устроены проверки 1C:EDT, где в них включается коннектор BSL LS и почему
замечания появляются в одних ситуациях и не появляются в других.

## Два независимых потока проверок

| | Xtext-валидация (встроенная) | ICheck («Проверки конфигурации») |
|---|---|---|
| Что это | «Живые» подчёркивания в редакторе, EDT запускает сам | Батчевые проверки объектов/проекта, включаются в `Свойства → Проверки` |
| Кто запускает | EDT: правка, открытие, сохранение, явная проверка | ПКМ «Проверить», фоновые прогоны самого EDT |
| Замечания | редактор + панель «Ошибки конфигурации» | панель «Ошибки конфигурации» |

Коннектор подключен к обоим потокам, но замечания в панель пишет **только
ICheck** — иначе hover в редакторе дублирует кнопки подавления
(`BSLValidator`, комментарий в шапке класса).

## Градация Xtext-проверок: FAST / NORMAL / EXPENSIVE

Тип задаётся аннотацией `@Check(CheckType.…)` на методе валидатора — у нас это
`BSLValidator.java`:

| Метод | Тип | Когда выполняется |
|---|---|---|
| `validate()` | `NORMAL` | открытие, сохранение и любые «большие» прогоны |
| `validateExpensive()` | `EXPENSIVE` | только в глубоком анализе (`BslResource.isDeepAnalysing()`) |

`FAST`-методов коннектор не регистрирует — при наборе текста LS не будится.

Прогоны Xtext **накопительные**: каждый режим выполняет и все более дешёвые типы:

| Событие | Выполняются методы |
|---|---|
| правка кода (после паузы — джоба «Расширенная проверка модулей») | `FAST` + `NORMAL` + `EXPENSIVE`* |
| открытие / сохранение | `FAST` + `NORMAL` |
| ПКМ «Проверить» | `FAST` + `NORMAL` + `EXPENSIVE` |

\* «Расширенная проверка модулей» EDT — это EXPENSIVE-проход; из-за накопительности
в нём выполняются и дешёвые типы, поэтому замечания обновляются после правки.
Оба наших метода вызывают один и тот же `LsCheckSupport.validateFromXtext`;
дублирующий заход в LS гасится кэшем `LsModuleAnalyzer` (ключ `uri + hash(content)`).
Планируется оставить только `NORMAL` — [issue #16](https://github.com/malikov-pro/bslls-connector-for-edt/issues/16).

## Как коннектор будит BSL LS

`LsCheckSupport.validateFromXtext` → `LsModuleAnalyzer`:

1. `LSService.ensureStarted()` — процесс LS (native/jar) поднимается при первом обращении.
2. Модуль отправляется в LS: `didOpen` (если модуль ещё не открыт) или `didChange`.
3. Ожидание публикации диагностик до 10 секунд (опрос 250 мс), статус-бар показывает занятость.
4. Результат кэшируется; все ~187 ICheck-проверок модуля делят этот один прогон,
   каждая фильтрует свой код (`plugin.xml` → `BslLsDiagnosticCheck:<Код>`).
5. После Xtext-фазы коннектор ставит ICheck-проверки BSL LS в очередь на этот модуль
   (`ICheckScheduler.scheduleValidation`) — замечания в панель появляются из ICheck.

## Сценарии

- **Набираете код** — через паузу EDT запускает «Расширенную проверку модулей», LS будится, замечания обновляются.
- **Открыли модуль / Ctrl+S** — то же через `NORMAL`.
- **ПКМ «Проверить» на модуле** — глубокий прогон типовых проверок EDT + наш канал; объём — выбранный модуль.
- **ПКМ «Проверить» на проекте** — батч ICheck по всем модулям, LS на каждый (с кэшем).
